# Effect v4 beta.106 API audit

**The design record is buildable, but not copy-pasteable.** Every load-bearing structural claim survives contact with `effect@4.0.0-beta.106`, `@effect/sql-sqlite-bun@4.0.0-beta.106` and `@ai-hero/sandcastle@0.12.0`: suspension really does interrupt the fiber so a local sandbox scope unwinds, replay really does memoize only Activity results, the cluster engine really does run single-node on one SQLite file, a gate deadline really is testable through `TestClock` with no wall-clock waiting, and Effect really is absent from Sandcastle's published types. What does not survive is the code: of the six TypeScript snippets in `typescript-effect.md`, three contain lines that do not compile (`yield* DurableDeferred.make`, `Schema.optionalWith`, `ParseError`) and one contains a live bug (§8's `while (true)` gate loop, which after the first rejection never suspends again because a `DurableDeferred` is keyed by name and `deferredDone` refuses to overwrite). **The single biggest problem is that §6 builds every Kojo error on `Data.TaggedError`, which is not a `Schema`** — and `Workflow.make`'s `error` option is typed `Error extends Schema.Top`, with the engine persisting completed runs as `Schema.Exit(success, error, Schema.Defect())`. As written, Kojo's typed error channel cannot be a workflow's error channel and cannot survive the suspend/resume round trip that the whole design exists for. The fix is mechanical (`Schema.TaggedError`, verified to preserve D8's `catchTags` behaviour exactly), but it touches every error in the codebase and it is the kind of thing that is very expensive to discover at phase 4.

Probe install: `<probe>/` — referred to below as `<probe>`.

## Design-critical answers

**Does suspension interrupt the fiber so a local scope unwinds? Yes — settled empirically, not by reading.** A workflow under `WorkflowEngine.layerMemory` with `Effect.acquireRelease` inside `Effect.scoped` wrapping a `DurableDeferred.await` logged, on its first pass: body entered / activity ran / SANDBOX acquired / (suspend) / **SANDBOX RELEASED** — the local finalizer fired at suspension, before the gate was answered. The path is `DurableDeferred.await_` → `Workflow.suspend(instance)` → `instance.suspended = true` → `fiber.interruptUnsafe(fiber.id)` → ordinary interrupt unwinding → local scope closes → `intoResult` converts the interrupt-only cause into `Workflow.Suspended` (`Workflow.ts:656,894`; `DurableDeferred.ts:143`). §3's "the container stops and the worktree is preserved, exactly as a normal interrupt would" is accurate, and D3 stands. The complement also holds: `Workflow.scope`'s docstring says it "closes the scope only when the workflow execution fully completes", and `intoResult`'s `Effect.onExitPrimitive` (`Workflow.ts:706-714`) calls `Scope.close` only on failure or `Complete` — the `Suspended` branch returns `Effect.void`. §3's "never do this for a sandbox" is correct. **One caveat that constrains where the scope may go:** `Activity.make` wraps every body in `retryOnInterrupt` — `Effect.retry` while `attempt <= 10 && Cause.hasInterrupts(...)`, then `Effect.die("Activity … interrupted and retry attempts exhausted")` (`Activity.ts:186-204`). The tear-down story works *because* `sandboxed` is a scope around activities. Put the sandbox scope inside an activity and the run dies instead of suspending.

**Does `withCompensation` skip nested activities? Yes — confirmed empirically, exactly as the doc says.** Compensation on a top-level effect ran; compensation wrapping an activity from the top level ran; compensation registered *inside* an activity body did not. The mechanism: `addFinalizer` attaches to `WorkflowInstance.scope`, and an activity body executes under a fresh throwaway instance (`WorkflowInstance.initial(...)`, `WorkflowEngine.ts:711`) whose scope closes with the activity's own success exit, where the finalizer no-ops. §3's quoted gotcha is verbatim from the source docstring. One refinement: the module-level `Workflow.withCompensation` types `cause` as `Cause.Cause<unknown>` while the workflow **method** version types it `Cause.Cause<Error["Type"]>` — prefer `myWorkflow.withCompensation`. `Workflow.addFinalizer` is confirmed to survive a two-day gate, because `intoResult` never closes the instance scope on a `Suspended` result.

**Is runner liveness queryable? Yes — the ADR's premise is satisfied by the framework, and there is a trap next to it.** `cluster_runners(machine_id, address, runner, healthy, last_heartbeat)` is created and maintained by `SqlRunnerStorage` (`cluster/SqlRunnerStorage.ts:237-247`). The heartbeat is `UPDATE cluster_runners SET last_heartbeat = CURRENT_TIMESTAMP WHERE address = ?` (`:742`), driven by Sharding's shard-lock loop on `Schedule.fixed(shardLockRefreshInterval)` = 10 s, and it fires even for a runner holding zero shards (`probeShardLocks = runnerStorage.refresh(selfAddress, [])`, `Sharding.ts:552`). `RunnerStorage.getRunners` already applies the staleness filter — `WHERE last_heartbeat > datetime(CURRENT_TIMESTAMP,'-35 seconds')` (`:706`, window = `shardLockExpiration`). So `GET /api/health` is a query against that table, or a standalone read-only `SqlRunnerStorage.layer` over the same `SqlClient` (constructible from `SqlClient + ShardingConfig`, no Sharding, no Crypto). **Kojo does not need its own heartbeat.** The trap: `SingleRunner.layer()` wires `RunnerHealth.layerNoop`, whose `isAlive` is `() => Effect.succeed(true)` for any address (`RunnerHealth.ts:51`). A Console implementing liveness through `RunnerHealth` always reports alive — producing precisely the "approved ✓ that means nothing" the ADR was written to prevent. Two more facts the Console UI must handle: Sharding calls `unregister` on graceful shutdown (`Sharding.ts:1583`), so a cleanly-stopped `kojo watch` leaves **no row** — "no rows" is the normal idle state, not an error; and a crashed runner leaves a stale row for up to 35 s, so the `last_heartbeat` filter is mandatory rather than optional. Separately, the ADR's rejection reason for "kojo ui hosts the engine" — *a second runner against one SQLite file* — is avoidable rather than inherent: registration, shard locks and the storage inbox are all guarded by `if (initialRunnerAddress)` (`Sharding.ts:290,591,1054`), so `SingleRunner.layer({ shardingConfig: { runnerAddress: Option.none() } })` yields a client-only Sharding that enqueues messages without becoming a runner. Record-and-apply is still the simpler design; the stated reason is just weaker than it reads. Latency note for §9 of console.md: a gate answer written by another process is picked up on `entityMessagePollInterval`, **10 s by default** — "applied, the run resumed" can lag the click by that much.

**Is a gate deadline testable through TestClock? Yes — proven, with two ordering hazards.** `DurableClock` uses the Effect `Clock` service on both of its paths, never wall time: below `inMemoryThreshold` it is `Activity.make({ execute: Effect.sleep(duration) })`; above it, `engine.scheduleClock` under `layerMemory` is `deferredDone(...).pipe(Effect.delay(duration), FiberMap.run(...))`, and `Effect.delay`/`Effect.sleep` route through `clockWith` reading `ClockRef` (`effect/src/internal/effect.ts:6067`), with `Clock.Clock` declared `Context.Reference` (`Clock.ts:189`) so the forked clock fiber inherits the TestClock. Measured: a **7-day durable sleep completed in 371 ms** wall after `TestClock.adjust("7 days")`; a 30-second one in 1 ms (`<probe>/durable-clock.test.ts`). The full §3 gate-deadline mechanism was built as written and both branches resolve: expiry in 134 ms wall for a 2-day virtual deadline, and a human answer via `DurableDeferred.succeed` before the deadline (`<probe>/gate-deadline.test.ts`). `it.effect` already provides `TestEnv = Layer.mergeAll(TestConsole.layer, TestClock.layer())` (`@effect/vitest/src/internal/internal.ts:44`), so no explicit `TestClock.layer` is needed. The hazards §10's one-line recipe hides: (a) `TestClock.adjust` only releases sleeps registered *before* it runs, so the test must let the workflow fiber actually reach the durable sleep — adjusting too early parked a 7-day sleep through a 30 s vitest timeout, twice; (b) after the deferred completes, `layerMemory`'s top-level `execute` is itself parked in its `suspendedRetrySchedule` sleep, also on the TestClock, so `Fiber.join` stays PENDING until an extra bare `TestClock.adjust("1 second")`. Kojo needs a test helper that encapsulates settle → adjust → settle → adjust.

**Can the cluster schema and the trace schema share one SQLite file? Yes — it was run.** One `SqliteClient.layer` with `SqlMessageStorage.layer` and a Kojo trace migrator on top produced `["cluster_messages","cluster_migrations","cluster_replies","kojo_migrations","phases"]` in a single database. The mechanism is table prefixing on both sides: the cluster prefixes everything with `cluster` including its own migration ledger, which **overrides** Migrator's package default of `effect_sql_migrations` (`SqlMessageStorage.ts:76-83`; `Migrator.ts:110`). Kojo must pass `table: "kojo_migrations"` explicitly — the default is at least distinct, but it is a name Kojo does not own. Three qualifications. First, "share one file" means **share one `SqlClient`**: the tag is a single `Context.Service` under `"effect/sql/SqlClient"`, so merging two `SqliteClient.layer` calls for the same file silently resolves to one client, and two separately-built contexts are two `bun:sqlite` handles with two independent `Semaphore.make(1)` serializers (`SqliteClient.ts:199-202`) — the driver's write serialization does not span them. The correct shape is one client layer, provided once, with cluster storage and the trace migrator both above it. Second, `busy_timeout` is 0 (above). Third, migration rows are INSERTed *before* the migration bodies run, inside one transaction, and a unique-constraint conflict there is read as `kind: "Locked"` and then swallowed as a debug log returning `[]` (`Migrator.ts:261-312`) — so a concurrent `kojo watch` and `kojo run` racing to migrate can leave one of them proceeding against a database it never verified. Combined with `busy_timeout = 0` that is a real startup race. Also: a failing migration is `Effect.die`, not a typed error (`Migrator.ts:206-218`, plus `Effect.orDie` around the cluster's own migrator), so console.md §10's "database schema older than the Console — warn loudly" must be implemented by inspecting the migration table before building the layer, not by catching anything.

**Does Effect leak into Sandcastle's public types? No — and the check is machine-enforced.** Across all ten published `.d.ts` files the only occurrence of the word is prose in the `CwdError` docblock explaining that its shape is re-declared as a plain `Error` subclass "so that Effect's type machinery does not leak into Sandcastle's published `.d.ts` files"; `package.json`'s postbuild runs `scripts/check-public-types-effect-free.mjs`. §1's version-independence argument holds, and the plan to invert the check for Kojo (assert no bare `Promise` in Kojo's public types) is sound. **But there is a consequence §9.5 does not account for:** Sandcastle bundles Effect 3.20.0 into `dist` — `effect@^3.20.0` is a devDependency and tsup inlines it (`dist/index.js` imports `Effect_exports`/`Layer_exports`/`Fiber_exports` from a local chunk; the recovered sourcesContent contains `moduleVersion = "3.20.0"`). A Kojo process runs two Effect runtimes side by side. No peer conflict, no dedupe fight — but nothing propagates: Sandcastle's fibers, FiberRefs and tracing context are invisible to Kojo's v4 runtime. §9's "Correlation across the sandbox boundary" cannot lean on Effect tracing reaching into Sandcastle; the only seams are the `logging.onAgentStreamEvent` callback and `exec`'s `onLine` callback, which is exactly why the `KOJO_RUN_ID` environment injection the doc already specifies is load-bearing rather than belt-and-braces.

## Non-blocking notes

**Workflow engine.** `Workflow.CaptureDefects` exists and **defaults to true** (`Workflow.ts:911`) — it decides whether a defect becomes a `Complete` carrying a failed Exit (recorded, run marked finished) or propagates. §6 is silent on it, and the default is probably not what Kojo wants for an agent crash that should page a human. `Activity.make` has an undocumented `interruptRetryPolicy` escape hatch. Suspension **waits for sibling activities**: `wrapActivityResult` + `waitForZero` (`Workflow.ts:719-766`) block a suspending fiber until every concurrently-running activity finishes or itself suspends — so a gate in lane A waits on a long agent phase in lane B before either sandbox releases. §3's `Workflow.suspend` prose should not read as author-facing: it takes `WorkflowInstance["Service"]` as an argument; authors reach suspension only through `DurableDeferred.await` or `DurableClock.sleep`. Two auditors characterise `layerMemory` differently: §3 calls it "wrong for anything that suspends", while the workflow auditor found it suspends and resumes correctly *in-process* and loses only a **process restart** (`executions`, `activities`, `deferredResults` are plain `Map`s). Both are consistent; the doc's wording is just stronger than the failure mode.

**Testing.** `ClusterWorkflowEngine.layer.pipe(Layer.provide(TestRunner.layer))` runs the **real cluster engine** with zero SQL — message envelopes, entity mailboxes, DurableClock wakeups — which `layerMemory` (a separate hand-rolled implementation) does not exercise. Worth naming in §10 alongside `layerMemory`. `@effect/vitest`'s peer range is `>=4.1.0 <5.0.0`, pinned to 4.1.10 in its devDependencies — write it as `>=4.1 <5`, not `≥ 4.1`. `effect`, `@effect/vitest` and `@effect/opentelemetry` ship `AGENTS.md` and an `ai-docs/` tree in their published files; `ai-docs/src/09_testing/10_effect-tests.ts` is a compiled example of exactly §10's idiom and is worth citing rather than hand-writing. `Effect.forkDaemon` does not exist on beta.106 (only `forkChild` at `Effect.ts:16944` and `forkIn` at `:16987`), and `Effect.fork` does not exist either — v3 muscle memory that will show up when someone writes the trace-writer fiber.

**CLI.** Deep non-barrel imports resolve (`effect/unstable/cli/Command`, `/Flag`, …) via the `"./*"` export, so the repo's no-barrel rule survives contact with Effect 4; only `internal/*` and `*/index` are blocked. The parent-reading pattern (`const root = yield* kojo` in a child) creates a genuine two-file ESM cycle with no barrel to break it — it runs, but it constrains `src/cli/`'s layout. Five global flags are already claimed before Kojo declares anything: `--help/-h`, `--version/-v`, `--wizard`, `--completions`, `--log-level` — note `-v` is version, not verbose. `Command.wizard` and `--wizard` already build an argv array interactively, and `Flag.withFallbackPrompt`/`Argument.withFallbackPrompt` turn a missing required flag into a prompt — some of what §11 describes for `kojo init` ships free. `Command.runWith(command, { version })(argv)` plus `Stdio.layerTest` is the CLI's unit-test seam. `Flag.withDefault` is typed `Flag<A | B>`, so a default outside a `Flag.choice` set compiles silently and widens the handler's parameter — `--sandbox`'s default needs `as const`. `Command.Environment` drags in `ChildProcessSpawner` unconditionally, even for a CLI that spawns nothing.

**HTTP.** Routes are **Layers whose error type is carried in the requirement channel** — `HttpRouter.add` returns `Layer<never, never, HttpRouter | Request.From<"Requires",…> | Request.From<"Error", E>>` (`HttpRouter.ts:502`), so an unhandled handler error surfaces as an unsatisfied requirement at `serve`, not as a Layer error. `HttpServerResponse.json` alone injects `HttpBodyError` there. Worth one sentence. `HttpStaticServer` already ships the path-traversal guard console.md §7 says to port from SSSF — plus byte ranges, ETag/Last-Modified and 304 (`resolveFilePath`, `:377`) — so the ported guard is needed for `ArtifactReader`'s id segments but must not be described as protecting the static build. `HttpRouter.toWebHandler` (`:1332`) returns a fetch handler with no port bound, which is the cheapest entry point for console.md §11's browser tier, and `BunHttpServer.layerTest` starts on an ephemeral port with a preconfigured client. `@effect/platform-bun`'s HTTP types need `@types/bun`; with `skipLibCheck: true` it degrades silently to unchecked arguments, without it you get `TS2307`/`TS2503`. If the §7 API is ever meant to be typed end-to-end, `effect/unstable/httpapi` (HttpApiBuilder / HttpApiClient / HttpApiScalar) is a different subpath and is what effect's own docs teach as the default — the hand-rolled `HttpRouter` path compiles and works, but gets no OpenAPI, no generated client, no schema-checked route contract.

**SQL.** WAL is on by default and can only be turned *off* (`disableWAL`) — §9's "one SQLite file in WAL mode" costs zero configuration. But the pragma is guarded by `!readonly`, so a read-only Console against a fresh path opens a non-WAL file; the first writer must create the database. `SqlSchema.findAll/findOne/findOneOption` decode rows through `Schema` and encode the request too, with decode failures landing in the typed channel as `SchemaError` — that extends §5's single-contract claim to the trace reader and removes hand-written row mapping. Column-name transforms are opt-in per client and off by default (`run_id`, not `runId`); sharing one client with the cluster is safe even with transforms on, but only because `SqlMessageStorage` defends itself with `.withoutTransforms()` (`:74`). `Migrator.fromRecord` is the loader for a bundled CLI — plain Effects in a source record, no dynamic import, no `FileSystem` requirement; `fromFileSystem` uses a bare `import()` that will not survive bundling. `schemaDirectory` is **dead** on sqlite-bun (the `dumpSchema` implementation is commented out, `SqliteMigrator.ts:34-76`), so there is no checked-in `_schema.sql` to review in a PR. `SqlRunnerStorage` reserves an advisory-lock connection on PostgreSQL/MySQL only; on SQLite shard locks fall back to the `cluster_locks` table. `SqlClient.reactive` exists and `SqliteClient.layer` provides Reactivity, but the module header says "Process-local invalidation" — it cannot replace §9's polling cursor for a Console in a separate process. `SafeIntegers` defaults false, so INTEGER columns arrive as JS numbers (fine for rowid cursors; relevant if a trace column ever holds a cluster snowflake). `ShardingConfig.runnerAddress` defaults to `localhost:34431` for **every** process under `layerFromEnv`, so two Kojo runners on one machine upsert the same `cluster_runners` row and contend for the same shard locks.

**Sandcastle.** `fork()` exists alongside `resume()` on both `RunResult` and `SandboxRunResult` — one-iteration session fan-out leaving the parent JSONL intact (their ADR 0018). The design record does not mention it at all, and it maps cleanly onto a parallel-agent phase: one planning session forked into N implementers. Caveats: fork isolates the session, not the branch, so concurrent forks need distinct branches; and pi's `buildPrintCommand` destructures only `{ prompt, resumeSession }`, silently dropping `forkSession` and `dangerouslySkipPermissions` — a `fork()` on `kojoPi` would mutate the parent session unless Kojo implements the flag. `run()` now owns a **structured-output correction loop**: `Output.object({ tag, schema, maxRetries })` makes it resume the failed session with generated feedback and recurse on `StructuredOutputError`. That is the same job as §6.1, and it is available only on the top-level `run()` which Kojo does not use — worth stating so the overlap reads as deliberate reimplementation rather than an oversight. `CreateSandboxOptions` has **no `env`** (every other entry point has one), so per-run secrets must be threaded by constructing a fresh provider inside `resolve(config)`. The `Sandbox` handle **survives abort** — per the `signal` docblock, an AbortSignal cancels the in-flight agent, not the container — which is the natural bridge for Kojo's suspension: Effect interruption drives an AbortSignal into `sandbox.run()`, then the scope's release calls `close()`. `tag` is **stripped from the published types**: internally `SandboxProvider` is a discriminated union on `"bind-mount" | "isolated" | "none"` and every gate dispatches on it, but `dist/SandboxProvider-EkSMuBp8.d.ts` exposes only `{ name, env, sandboxHomedir? }`, `IsolatedSandboxProvider` and `NoSandboxProvider` are structurally identical, and `docker()`/`podman()` are typed as the wide union — so Kojo cannot statically derive resume capability from a provider value and must carry its own tag. `ParsedStreamEvent` is the return type of the required `parseStreamLine` but is **not exported**, so `kojoPi` must infer it (`ReturnType<AgentProvider["parseStreamLine"]>`). Worktree refresh has **four** skip paths, not the two §7 lists: HEAD not on the branch (a paused or mid-rebase worktree — exactly the state a suspended run leaves), fetch failure, local divergence from `origin/<branch>`, and a dirty worktree; each logs and reuses as-is. Since "the branch is the durable state" is the central claim, edge 3 in architecture.md §8 needs to know that on replay the worktree may legitimately be behind origin with nothing louder than a log line. `@standard-schema/spec` does resolve in practice, because `effect@4.0.0-beta.106` declares it as a direct dependency — declaring it directly is still right, but it is undeclared load-bearing surface rather than a missing module. pi's session-storage asymmetry is sharper than §7 states: the Claude and Codex helpers **are** public (`dist/index.d.ts:32-58`); only pi's are private, along with `makePiSessionStorage`. `kojoPi` must reimplement pi's cwd encoding, the sandbox-side JSONL locate, and the transfer rewrite — including the quirk that pi resolves `--session <id>` against the *current project's* encoded directory, so a captured file must land under the encoded **host** cwd or pi hangs on a "fork session?" prompt in json mode.

**Left unclear.** §1's claim that `@effect/cli@0.77.0` is a v3-only artefact peering on `effect: ^3.22.1` could not be settled — the package is not in the probe install. What *is* settled is the practical half: `effect/unstable/cli` is complete and self-sufficient at beta.106, so §1's advice holds regardless of the standalone package's status.
